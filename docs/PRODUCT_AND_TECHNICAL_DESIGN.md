# 产品与技术设计方案

## 1. 产品定位

**产品名称：基金阶梯账本（Fund BOLL Ledger）**

面向个人投资者的场内基金手动价格计算与交易记账小工具。它不是行情终端、投顾系统或交易软件。价格由用户从外部行情页面手动查看后录入；成交价、份额、费用也由用户手动记账。

### 主要用户任务

1. 录入某一只基金的 BOLL 上轨、中轨、下轨、昨日收盘价、上一次成交价和当前价格。
2. 立刻看到当前价格相对五个参考价的涨跌额、百分比和位置。
3. 查看任一参考价向上/向下 1%—10% 的阶梯，并识别当前价已经越过哪一档、下一档在哪里。
4. 手动记录场内基金买入、卖出和东方财富账户实际收取的费用。
5. 根据完整交易记录计算持仓数量、加权平均成本、已实现盈亏和浮动盈亏。
6. 保存每日价格观察、导出完整备份，在更换设备时手动恢复。

## 2. 产品边界与不变量

### 明确不做

- 股票个股交易管理；只围绕用户自行创建的场内基金档案。
- 东方财富登录、行情抓取、账户同步、订单提交、自动交易。
- 自动推断不同基金/交易方式/券商账户实际适用的费率与税费。
- 第一版云端同步。IndexedDB 数据只存在当前浏览器的站点存储中。

### 必须保持的不变量

- 一个基金档案独立关联其价格、交易、费用参数和价格快照。
- 基准价格与当前价格分开；上一次成交价与昨日收盘价分开。
- 每一档均从所选原始基准价单独计算，不连乘、不复利。
- 所有浮动盈亏必须基于当前参考价；当前价未输入时显示“未提供”，不能把空值当作零价格后展示虚假亏损。
- 费率估算不等于实际费用；实际交易账本以逐笔手工输入值为准。
- 卖出不可超出该成交时点的持仓数量。
- 删除/修改历史交易后，持仓成本与已实现盈亏重新计算。
- 不允许导入备份时静默合并或覆盖；必须明示将替换当前设备的数据，并让用户确认。
- 没有确认成功时，不显示已保存或已同步。

## 3. 信息架构

### A. 价格计算

顶部基金选择器；可编辑的五个参考价和当前价格；五基准比较卡；十档阶梯；保存价格快照入口。

输入字段：

- BOLL 上轨
- BOLL 中轨
- BOLL 下轨
- 昨日收盘价
- 上一次成交价（允许手动改写；可从最近一笔交易带入）
- 当前价格（由用户手动输入）
- 每只基金的最小价格变动单位（默认 0.001 元，可更改）

五个参考基准分别展示当前价与基准的涨跌额、涨跌幅、基准上方/下方/相同。阶梯面板选择任意基准与方向，显示 10 行价格、档位状态、当前涨跌幅和下一档价格。

### B. 交易账本

记录字段：

- 成交日期时间
- 买入/卖出
- 成交价格（元/份）
- 成交数量（整数份）
- 实际佣金
- 经手/过户等费用
- 印花税
- 其他费用
- 备注

允许新增、编辑、删除。每次写入前重新计算整只基金的交易序列；若任何时点发生超卖，则拒绝保存并指出问题交易。

### C. 持仓盈亏

- 当前持仓份额
- 剩余持仓成本
- 加权平均单位成本（后续 UI 可加）
- 当前参考市值
- 已实现盈亏
- 浮动盈亏
- 累计已记录费用

汇总页按基金列出上述数据。当前参考价缺失时，市值/浮动盈亏应标记未提供；不可将缺少价格当成有效的零价。

### D. 历史与备份

- 手动保存价格快照，保存时间、交易日期、五个参考价、当前价格、价格单位与备注。
- 删除快照。
- 完整 JSON 备份/恢复。
- 交易明细 CSV 导出，供 Excel 检查；CSV 不是完整备份格式。

## 4. 计算与财务口径

### 价格阶梯

对于基准价 `P`，方向 `d` 和档位 `n ∈ [1,10]`：

- 上涨：`P × (1 + n / 100)`
- 下跌：`P × (1 - n / 100)`

计算值最后按基金档案中配置的 tick size 四舍五入。默认 tick size 为 `0.001` 元，用户应按实际基金规则校验。显示值可能导致重新计算出的真实百分比略偏离整数刻度，因此当前相对涨跌幅始终用当前价格与原始基准计算，而不是从阶梯文字反推。

### 档位状态

- 上涨档：当前价 `>=` 该档价格视为“已越过”。
- 下跌档：当前价 `<=` 该档价格视为“已越过”。
- 第一条尚未越过的档位是“下一档”。
- 实际涨跌幅超出对应方向 10% 时提示“超出十档范围”。
- 当前价或基准价缺失/非法时不猜测状态。

### 交易金额与成本

- 成交金额 = 单价 × 份额，结果四舍五入到分。
- 买入增加份额，增加的成本 = 成交金额 + 买入费用。
- 卖出费用 = 佣金 + 经手/过户等 + 印花税 + 其他费用。
- 卖出已实现盈亏 = 卖出成交金额 − 卖出费用 − 本次卖出份额所分摊的加权平均成本。
- 部分卖出按卖出前剩余成本和份额计算成本分摊；全部卖出时将所有剩余成本归零，避免残留分币。
- 浮动盈亏 = 当前参考市值 − 剩余持仓成本；不预估未来卖出费用。

### 费用录入

基金档案中允许录入佣金费率、可选最低佣金规则，仅为生成佣金估算。佣金率按“百分比”输入，例如 `0.025` 表示 `0.025%`。经手/过户费用、印花税和其他费用逐笔手动输入，不按基金类型硬编码。最终实际成本以用户核对的东方财富成交明细/交割单为准。

## 5. 技术架构

### 客户端

- React + TypeScript：页面与数据模型。
- Vite：开发服务器、类型检查前置构建及生产构建。
- IndexedDB：本地结构化数据持久化。
- PWA manifest + Service Worker：可安装入口与基础静态资源缓存。
- CSS media queries：桌面/手机响应式布局，不维护两套界面。

### 数据流

输入组件 → 规范化/验证 → 纯计算函数 → React 页面即时呈现 → IndexedDB 延迟写入 → 导出/恢复。

费用/盈亏函数与界面解耦，以纯函数为主，方便测试；所有外部数据获取和交易 API 均不在架构内。

### 目前的持久化策略

`fund-boll-ledger` IndexedDB 数据库以一个 `app-state` 记录保存版本化 AppData。MVP 体量下该策略容易备份，缺点是每次保存写入整个状态、多个标签页同时编辑可能发生后写覆盖。下一阶段若需要多标签并发或云同步，应升级到按基金、交易、快照分别存储并添加版本检查，而不是直接把本地状态上传。

## 6. 数据模型

### Fund

`id, name, code, market, category, tickSize, commissionRatePercent, minimumCommission, applyMinimumCommission, prices, notes, createdAt, updatedAt`

### FundPrices

`upper, middle, lower, previousClose, lastTradePrice, currentPrice`。使用空字符串表示“尚未输入”，不以 0 代替缺失。

### Trade

`id, fundId, tradedAt, side, price, quantity, commission, transferFee, stampDuty, otherFee, feesChecked, note, createdAt, updatedAt`

### PriceSnapshot

`id, fundId, createdAt, tradingDate, prices, tickSize, note`

### AppData

`schemaVersion, funds[], trades[], snapshots[]`，当前 schemaVersion 为 1。将来更改 schema 时必须实现显式迁移和迁移测试。

## 7. 安全、隐私和恢复

- 默认不上传用户基金、持仓或交易信息。
- 浏览器站点存储可能被清理、浏览器配置文件重置或设备故障影响；必须定期导出 JSON。
- JSON 恢复会替换当前设备中的完整数据，覆盖前必须二次确认。
- 导入时检查 schemaVersion 与必要字段，不将任意 JSON 直接当成有效账本。
- 首版不加账号/密码，不收集敏感认证信息。
- PWA 在非 HTTPS 生产地址可能无法安装或启用 Service Worker；本地开发 `localhost` 除外。

## 8. 分阶段实施计划

### 阶段 0：基础与验证（当前交付）

创建 PWA、版本化数据模型、本地保存、五基准、十档、基金档案、交易新增/编辑/删除、加权平均成本、费用字段、快照、备份、CSV、核心单元测试。

通过门槛：`npm run test` 通过；`npm run build` 通过；手动完成一只基金从创建、价格输入、买入、卖出、盈亏、快照、导出、重新导入的完整流程。

### 阶段 1：本地验证后修复

- 根据真实场内基金案例核验价格档位和价格舍入。
- 对比东方财富成交明细，核对佣金、其他费用以及费用是否重复。
- 补足边界测试：空值、负值、小数价格、费用为零、部分卖出、全部卖出、历史交易回填、删除交易后重算、备份导入错误与覆盖提示。
- 在 Windows Edge/Chrome 与 Android Chrome 验证响应式布局、PWA 安装、离线重新打开和 IndexedDB 权限。

### 阶段 2：账本可靠性

- 交易编辑/删除前显示影响范围。
- 增加完整账本校验报告、备份时间提示、恢复前自动下载当前数据。
- 将当前单记录 IndexedDB 拆成 stores 或引入 Dexie 等经过验证的 IndexedDB 封装；为 schema 增加迁移。
- 引入跨标签页写入协调、导入时的交易时序校验与修复报告。

### 阶段 3：跨设备同步（只有明确需要后才做）

先明确认证提供方、数据保留、备份、冲突与删除语义；使用可控的同步服务和用户授权。每个写入需要版本号/更新时间、幂等 ID 和冲突界面。同步成功必须收到服务端确认，不能仅凭网络请求发出就显示同步完成。

### 阶段 4：可选增强

- 更灵活的自定义阶梯范围（仍默认十档）。
- 成交记录筛选、月度费用汇总、按基金/日期检索。
- 导出含价格快照的 CSV/Excel 兼容报告。
- 自定义手续费模板与费用核对状态。

## 9. 风险、权衡与当前取舍

| 方案 | 主要优点 | 主要代价/风险 | 当前选择 |
|---|---|---|---|
| 本地 IndexedDB | 隐私边界清晰、无服务费、离线可用 | 不会自动跨设备同步；浏览器数据可能丢失 | 首版采用，必须提供 JSON 备份 |
| 立即做云同步 | 电脑手机可共享一份账本 | 需要身份认证、后端、冲突处理、安全维护 | 暂缓，不在未明确授权情况下上传交易数据 |
| 自动推断基金费用 | 少输入 | 容易用错账户费率、基金类别和收费项目 | 不采用，以逐笔实际费用为主 |
| 估算费用 + 实际值手动输入 | 可辅助计算，同时保留账本真实性 | 需要用户核对估算值 | 采用 |
| 用浮点数直接算金额 | 开发简单 | 可能出现分币误差 | 金额使用整数分，价格采用固定点计算 |

## 10. 开发验收定义

- 功能验收：五基准与当前价联动、十档双向定位、费用逐笔记录、持仓/盈亏重算、历史快照、备份恢复、CSV 导出全部可操作。
- 数值验收：核心公式有自动化测试；金额计算不使用二进制浮点作为唯一货币表示；价格 tick 可配置。
- 数据验收：刷新不丢数据；删除基金关联数据一致删除；交易超卖拒绝；导入覆盖前有明确确认。
- 设备验收：至少在 Windows 浏览器与 Android 浏览器测试小屏布局；生产 HTTPS 下测试安装和离线壳。
- 边界验收：当前价缺失不输出有效浮动盈亏；费用估算与实际费用区分；超出十档显示实际幅度。
